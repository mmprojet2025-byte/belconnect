# Audit critique de Belconnect avant lancement

20 octobre 2026 — dépôt `/Users/Malaba/Projects/belconnect`, base Git `17be8b7`, avec les modifications locales présentes lors de l’audit.

**Décision : ne pas ouvrir les paiements réels ni annoncer la V1 comme terminée.** Belconnect est une version de développement avancée, avec de vrais parcours métier et une présentation publique cohérente. Sa faiblesse principale est la fiabilité de bout en bout : incidents de paiement, exploitation, information juridique et parcours organisateur. Ajouter encore des fonctionnalités augmenterait le travail restant.

Le [plan de finalisation](PLAN_FINALISATION_V1.md) transforme les constats ci-dessous en lots ordonnés. Cet audit ne modifie pas les fonctions du site.

## Portée et preuves

Revue des parcours React, authentification et autorisations Spring, réservations, projets, Stripe Connect/Checkout/abonnements/webhooks, configuration, migrations et documentation de lancement. Inspection navigateur du catalogue projets sur ordinateur, de la fiche du projet numérique à 390 px et du catalogue/menu activités à 390 px. Les parcours authentifiés sont examinés dans le code et les tests API ; aucune opération n’a été faite sur les comptes personnels pour cette recette.

Les 46 tests contiennent parfois plusieurs scénarios dans une méthode : ce nombre ne mesure pas la couverture. Aucun pourcentage de couverture n’a été calculé. Pas de scan de vulnérabilités Java/conteneurs, pentest externe, essai de charge, audit WCAG complet, validation juridique, paiement Stripe réel, livraison SMTP externe ou restauration de production pendant cet audit. Les incidents financiers ci-dessous sont des scénarios déduits du code, pas des pertes d’argent observées.

Les maquettes et le cahier des charges sont représentés par le suivi présent dans le dépôt ; aucune certification de conformité exhaustive aux documents originaux ou comparaison pixel par pixel des archives Stitch n’est revendiquée.

## Ce qui est réellement solide

- L’API exige une authentification par défaut. CSRF reste actif pour les actions du navigateur ; les webhooks ont une vérification de signature distincte.
- Mots de passe BCrypt avec coût 12, rotation de session à la connexion, cookies HttpOnly/SameSite, invalidation après changement de mot de passe ou suspension.
- Les droits d’espace et de groupe sont vérifiés côté serveur. Plusieurs tests couvrent les accès interdits, les versions périmées et les opérations concurrentes.
- Les réservations gratuites disposent de contrôles de capacité et de concurrence. Les activités payantes ont déjà une reprise automatique et un traitement des remboursements plus aboutis que les projets.
- Les migrations Flyway, le schéma de test séparé et les clés d’idempotence constituent une base utile.
- Les fiches publiques ont une identité cohérente. Les projets présentent désormais leur objectif et distinguent aide, action payante et don.

Ces points justifient de terminer l’existant, sans réécrire le projet ni changer de framework.

## Priorités

**P0** : empêche le lancement public prévu. **P1** : à corriger ou à couvrir par une procédure vérifiée avant ouverture. **P2** : amélioration importante, mais report possible si le parcours reste honnête et utilisable.

« Confirmé dans le code » décrit le mécanisme constaté. « À valider » indique une vérification restante ; ce n’est pas une faille démontrée.

## Paiements et règles métier

### F01 — P0 — Le paiement réel n’est pas implémenté comme mode exploitable

**Confirmé dans le code.** `StripeConnectController.options`, `PaidProjectParticipationController:47`, `PaidActivityReconciliation:28` et les webhooks acceptent uniquement des préfixes/test modes. `StripeDonationWebhookController:43` et `StripeSubscriptionWebhookController:44` ignorent les événements live.

**Conséquence :** remplacer simplement une clé test par une clé live ne termine pas l’intégration. Certaines opérations seraient refusées et des notifications réelles ignorées.

**À faire :** configurer explicitement test/live, vérifier la cohérence clés/comptes/prix/webhooks, conserver le refus des mélanges et les garde-fous. Ouvrir le live seulement après la recette test des quatre flux. Aucun secret ne doit entrer dans Git ou le frontend.

### F02 — P0 — Un événement ancien peut réactiver un abonnement annulé

**Confirmé par lecture, reproduction Stripe restante.** `StripeSubscriptionWebhookController:46–79` applique un Checkout terminé comme `ACTIF/PRO` sans vérifier l’état actuel de l’abonnement chez Stripe. La branche `subscription.updated` peut également rétablir Pro après un événement `deleted`.

Scénario : abonnement actif → suppression reçue → ancien événement de fin de Checkout rejoué. Les identifiants restent identiques, donc la branche réactive Pro. La commission locale peut repasser à 5 %.

**À faire :** dédupliquer les événements et synchroniser avec l’état Stripe actuel ; ne pas se fier uniquement à un timestamp. Couvrir doublons, ordre inversé, impayés, renouvellement, résiliation et événement manqué. Stripe précise que l’ordre de livraison n’est pas garanti : [documentation officielle](https://docs.stripe.com/webhooks#event-ordering).

### F03 — P0 — Les places payantes des projets peuvent être revendues avant confirmation tardive

**Confirmé par lecture, concurrence à reproduire.** `PaidProjectParticipationController:64–65` cesse de compter une réservation en attente après son expiration locale ; `reserve:137–140` fixe 35 minutes. Le webhook `StripeDonationWebhookController:85–103` peut ensuite la passer à `PAYE` sans vérifier la capacité.

Scénario : dernière place payée sur Stripe avant expiration, notification retardée au-delà de 35 minutes ; une autre personne réserve la place libérée localement ; l’ancien paiement est ensuite confirmé. Le compteur affiché est borné à zéro et masque le dépassement.

**À faire :** libérer seulement après état Stripe vérifié, partager les verrous entre réservation/confirmation/annulation, ajouter une réconciliation. Tester avec une capacité de 1 et livraison tardive. Ne pas rejeter silencieusement un paiement effectivement encaissé : confirmer ou rembourser selon une règle explicite.

### F04 — P1 — La reprise des dons, projets et remboursements est incomplète

**Confirmé dans les chemins lus.** Les reprises planifiées trouvées concernent les activités. `PaidProjectParticipationController:197–228` dépend d’une nouvelle action manuelle pour reprendre des remboursements ; `StripeDonationWebhookController` ne traite pas les remboursements ou litiges. Une tentative de projet créée sans identifiant de session peut échapper à la fermeture des sessions.

**Conséquence :** statuts bloqués, remboursement Stripe non reflété dans le site, incident sans file de suivi. Pour les activités, les tentatives sans session ne sont actuellement que signalées dans les logs (`PaidActivityReconciliation:30–35`).

**À faire :** rapprocher régulièrement toutes les transactions avec Stripe, gérer les remboursements en attente/échoués et les incidents. Définir la procédure des contestations. Ajouter une liste opérationnelle minimale, pas un tableau de bord comptable complet.

### F05 — P1 — Une offre publique rattachée à un groupe peut être invisible aux visiteurs

**Confirmé dans le code.** `DraftController.visibility` autorise un projet public avec groupe. `ProjectPublicationController.PUBLIC_SELECT` le rend public. Mais `PaidProjectParticipationController:74–80` exige une appartenance dès que `groupe_id` existe, indépendamment de `visibilite`.

**À faire :** appliquer la même règle publique/privée à la fiche, à l’offre, au don et à la réservation. Tester un projet public rattaché à un groupe, puis le même projet privé. Il s’agit ici d’un refus abusif, pas d’une fuite démontrée.

### F06 — P1 — Le contrat d’une participation payante à un projet manque de précision

**Observé sur la fiche numérique et confirmé dans le modèle d’offre.** Le projet annonce six ateliers, mais vend une place pour « une séance », sans séance, heure ni lieu structurés dans `OfferInput` (`PaidProjectParticipationController:37`).

**Conséquence :** l’acheteur sait combien payer sans savoir précisément à quoi il s’inscrit.

**À faire simplement :** pour la V1, une offre décrit un rendez-vous déterminé avec date/heure, lieu, contenu et annulation, ou référence une activité existante. Ne pas construire un calendrier complexe de sessions avant d’avoir choisi ce contrat.

### F07 — P1 — Prix Pro et retour d’abonnement à fiabiliser

**Confirmé.** `SpaceSubscriptionController:81–90` vérifie 1 000 centimes et l’intervalle « month », mais pas le nombre de mois par intervalle. Le code n’établit pas à lui seul le traitement fiscal de « 10 € HT ». Le retour est `?abonnement=retour`, tandis que `AccountPage:20` ouvre la rubrique des espaces pour `stripe`, pas pour `abonnement`.

**À faire :** vérifier interval_count=1 et la configuration fiscale choisie ; afficher clairement le total avant engagement ; revenir à l’espace concerné et actualiser le statut après webhook.

**Décisions hors code :** frais Stripe, taxes, factures/reçus, remboursement des dons et responsabilité financière des litiges. Le plafond actuel de don à 100 000 € mérite également une décision explicite avant ouverture.

## Sécurité et exploitation

### F08 — P0 — La configuration actuelle est une configuration de développement

**Confirmé.** `application.properties:4–12` possède des valeurs locales et `spring.profiles.default=local`. Le cookie Secure vaut false par défaut. Le profil local charge les exemples. Aucun profil de production dédié ni procédure de déploiement/restauration automatisée n’a été trouvé dans le dépôt examiné.

Ce n’est pas une preuve que des mots de passe sont exposés sur Internet : les services Docker locaux sont liés à 127.0.0.1. C’est un risque si cette configuration est utilisée telle quelle pour publier.

**À faire :** échec au démarrage si configuration production incomplète ; URL HTTPS, secrets externes, cookie Secure, base distincte sans démos, reverse proxy, compte SQL limité et migrations contrôlées. Vérifier HSTS au point de terminaison HTTPS, sans conclure à son absence en production depuis le HTTP local.

### F09 — P1 — Protection contre les abus insuffisante pour une plateforme publique

**Confirmé.** `AuthController:190` limite par adresse distante, en mémoire, avec une fenêtre commune aux actions d’authentification. Pas de vérification de propriété de l’e-mail ni MFA dans les parcours lus.

**Risques :** inscription avec l’adresse d’un tiers, attaque distribuée, limite perdue au redémarrage ou incohérente entre instances, blocage collectif derrière un proxy mal configuré.

**À faire :** vérification d’e-mail, protection par compte et IP avec temporisation, configuration des proxys de confiance, limitations sur les opérations coûteuses. Protéger en priorité le propriétaire et les administrateurs qui gèrent l’argent ; MFA pour ces comptes recommandée avant ouverture.

### F10 — P1 — Aucune preuve de restauration et d’alerte opérationnelle

**Non validé.** Docker conserve les données dans un volume ; cela ne constitue pas une sauvegarde. Aucun exercice de restauration, supervision externe, procédure de retour arrière ou objectifs de perte de données/délai de reprise n’est attesté pour l’environnement cible.

**À faire :** sauvegardes chiffrées hors serveur, durée de conservation, restauration dans une base séparée, alertes sur indisponibilité/API/webhooks/remboursements et procédure d’incident. Définir qui reçoit et traite ces alertes.

### F11 — P1 — La récupération de compte dépend d’un service e-mail non validé

`AuthController.requestRecovery` prévoit un expéditeur SMTP et reste volontairement neutre en cas d’échec de livraison. Le test utilise un expéditeur de test ; la documentation distingue bien Mailpit d’un vrai service.

**À faire :** fournisseur, domaine d’envoi, SPF/DKIM/DMARC et test vers une vraie boîte. Surveiller les échecs côté exploitation sans révéler au demandeur l’existence d’un compte. Tester expiration, usage unique et invalidation des anciennes sessions.

### F12 — P1 — Chaîne de vérification incomplète

**Confirmé pour le dépôt.** Pas de `.github/workflows`, de suite navigateur automatisée ni de script de test frontend dans `package.json`. Les tests actuels passent, mais la gestion complète des abonnements et les incidents F02/F03 ne sont pas couverts par la suite examinée.

**À faire :** CI lint/build/tests/migrations, tests navigateur des quelques parcours critiques et scans Java/conteneurs/secrets. Garder les tests de concurrence et ajouter les incidents de paiement avant la recette réelle. Un `npm audit` à zéro n’est pas une certification.

### F13 — P2 — Durcissement complémentaire et limites d’audit

Les réponses API locales inspectées ont `nosniff`, `DENY` et `no-store`. Pas de CSP explicitement trouvée dans la configuration lue. Les saisies sont rendues via React et les requêtes SQL examinées sont paramétrées ; aucune injection exploitable n’a été démontrée.

À vérifier sur le site déployé : CSP adaptée aux images/Stripe, politique de référent, limites de taille de requête, logs sans mots de passe/jetons/messages privés, accès aux exports, protection des comptes GitHub/hébergeur/Stripe et rotation des secrets. La recherche de motifs dans l’arbre Git actuel ne remplace pas un scan de l’historique.

## RGPD, contrats et confiance

### F14 — P0 — Les pages légales ne sont pas disponibles en production

**Confirmé.** `App.tsx:37` et `:653` conditionnent la route et les liens à `import.meta.env.DEV`. Les textes sont des brouillons, et l’exploitant n’est pas encore identifié comme structure enregistrée.

**À faire :** finaliser l’identité de l’exploitant, les coordonnées et les textes ; les publier sur des routes stables accessibles sans connexion, y compris depuis inscription et paiement. Ne pas supprimer simplement le garde-fou pour publier les brouillons.

Les informations commerciales doivent être disponibles au bon moment du parcours : [SPF Économie](https://economie.fgov.be/fr/themes/entreprises/guidance/pratiques-commerciales/obligations-dinformation-dans).

### F15 — P1 — Les droits RGPD restent à rendre opérationnels

**Confirmé dans le périmètre lu.** Modification du prénom/nom disponible, mais aucun parcours complet d’accès/export/effacement du compte, politique de purge exécutée ou registre de traitement opérationnel trouvé.

**À faire :** contact privacy, procédure de vérification d’identité et suivi des demandes ; export et suppression/anonymisation avec conservation justifiée des éléments financiers. Une procédure manuelle contrôlée peut suffire au pilote : une interface complexe n’est pas indispensable. Tester réellement une demande et son effet sur les sauvegardes.

Faire correspondre finalités, bases juridiques, destinataires et conservations aux données effectivement collectées. La confidentialité ne se réduit pas à une case d’acceptation : [APD, droits des personnes](https://www.autoriteprotectiondonnees.be/professionnel/rgpd-/droits-des-citoyens).

### F16 — P1 — Responsabilités commerciales et traitement des abus non finalisés

La règle produit « aucun remboursement automatique si le participant annule » ne tranche pas à elle seule les droits légaux. Le dossier juridique identifie déjà les sujets ouverts : vendeur, frais, dons, taxes, mineurs, responsabilités des organisateurs, images et signalements.

**À faire :** relecture juridique belge ciblée ; identifier le vendeur/bénéficiaire avant paiement, distinguer don/achat/abonnement, versionner les conditions contractuelles et leur acceptation si retenue. Prévoir contact, signalement, décision et contestation simples, avec possibilité opérationnelle de suspendre un contenu ou compte problématique. La vue propriétaire actuelle ne constitue pas à elle seule un dispositif de modération.

La qualification DSA et ses éventuelles exemptions doivent être examinées selon l’activité et la taille réelles. Aucun besoin d’ajouter des publicités ou un bandeau cookies décoratif : consentement uniquement pour les usages qui l’exigent.

### F17 — P2 — Images externes et provenance des contenus

`DraftController:68–76` valide une URL HTTPS, puis `Projects.tsx:24,64` la charge directement. Cela ne garantit ni disponibilité, ni droits d’utilisation, ni absence de suivi par l’hôte de l’image.

**À faire :** galerie contrôlée pour la V1 ou hébergement maîtrisé, image de secours en cas d’erreur, règles de provenance/droit à l’image et politique de référent adaptée. Il ne s’agit pas ici d’une SSRF serveur démontrée : le chargement observé est côté navigateur.

Les images de démonstration ne prouvent pas l’existence des organisateurs/événements. Ne pas présenter les exemples comme une offre réelle.

## Expérience utilisateur, interface et accessibilité

### F18 — P1 — Une panne des activités bloque tout le site

**Confirmé.** `main.tsx` place toute l’application dans `CatalogProvider`. `CatalogContext.tsx:112–146` ne rend pas ses enfants tant que le premier catalogue n’est pas chargé ; `data.map(parseActivity)` rejette le lot si un élément est invalide.

**Conséquence :** projets, connexion, récupération de mot de passe et informations légales peuvent devenir inaccessibles à cause d’une panne d’activités.

**À faire :** rendre navigation et pages indépendantes du catalogue, états d’erreur locaux, possibilité de réessayer, limite d’erreur React pour éviter une page blanche. Tester une réponse 500, un timeout et un élément invalide sans arrêter l’application utilisée par le fondateur.

### F19 — P1 — Mon espace reste trop proche d’un outil de gestion

**Constat de structure, recette authentifiée restante.** `MyWorkspace.tsx:61–86` enchaîne espaces/groupes, abonnement, Stripe, annonces, activités, adhésions, demandes d’ouverture, projets, validation, publication et supervision. `AccountPage:71` monte aussi les rubriques masquées avec `hidden`, donc leurs chargements peuvent démarrer même lorsqu’elles ne sont pas affichées.

**À faire simplement :** une entrée « Participer » et une entrée « Organiser » ; choix d’espace si nécessaire ; tâches principales avant réglages. Sous Organiser : activités, projets, membres ; Stripe et abonnement dans les réglages. Garder l’examen des projets existant, mais ne pas exposer tout le circuit à chaque utilisateur. Charger la rubrique quand elle s’ouvre.

### F20 — P1 — Des boutons promettent un paiement qui n’est pas disponible

**Observé sur `/projets/2`.** Le panneau propose « Voir l’action à 12 € » et « Faire un don », puis les sections indiquent que les paiements ne sont pas ouverts.

**À faire :** refléter la disponibilité dans le panneau principal ; ne pas envoyer l’utilisateur vers une impasse. Après paiement, afficher un état de confirmation vérifié, une actualisation maîtrisée et un recours support si le statut ne se stabilise pas.

### F21 — P2 — Les favoris donnent une fausse impression de sauvegarde

`App.tsx:123` initialise les favoris dans un simple état React vide. Ils disparaissent au rechargement.

**À faire :** soit les persister proprement, soit retirer ce bouton de la V1. Ne pas consacrer un lot entier à une fonction secondaire.

### F22 — P2 — Erreurs et routes peu explicites

`lib/auth.ts:5` traduit par défaut un 403 en « Session expirée ». Une permission refusée n’est pas forcément une expiration. Le routage manuel d’`App.tsx` n’a pas de page générale dédiée aux URL inconnues ; le cas par défaut mène à l’accueil.

**À faire :** distinguer 401, 403, 404, 409, 429, panne réseau et paiement en attente ; conserver les saisies. Ajouter une vraie page introuvable et un retour clair. Ne pas afficher « démarrez le serveur Belconnect » à un visiteur de production.

### F23 — P2 — La hiérarchie visuelle est meilleure, la précision éditoriale reste inégale

**Observé/confirmé.** Les cartes projets et activités sont cohérentes. En revanche, « Les projets près de vous » ne s’appuie pas sur un champ de lieu dans le DTO projet. Les périodes d’un projet ne décrivent pas le rendez-vous acheté. Les boutons d’aide/don/action demandent encore trop d’explications négatives.

**À faire :** lieu réel ou titre neutre ; une phrase de résultat attendu, organisateur identifiable, date pertinente, action principale explicite. Conserver les trois distinctions : réserver une activité, proposer une aide, soutenir financièrement. Ne pas recopier la logique de réservation des activités sur tout le projet.

### F24 — P2 — Accessibilité partielle, pas validée

Points positifs observés : lien d’évitement, noms accessibles des actions, menu mobile avec état ouvert/fermé, champs libellés. Défaut structurel confirmé : `<main>` dans `Projects.tsx:76` est imbriqué dans le `<main>` d’`App.tsx:268`.

**À faire :** un seul repère principal, niveaux de titres cohérents, parcours clavier complet, focus après navigation/erreur, zoom 200 %, contraste mesuré, validation avec lecteur d’écran. Les contrôles à 390 px ne prouvent ni l’accessibilité ni la compatibilité sur un véritable téléphone. Référence : [WCAG 2.2](https://www.w3.org/WAI/WCAG22/quickref/).

## Performance, maintenabilité et périmètre

### F25 — P2 — Chargement global et listes sans limite

Build web : environ 116 kB de JS compressé, ce qui ne justifie pas une réécriture. Mais `App.tsx` importe les fonctions privées avec le site public ; le catalogue projets charge et filtre toute la liste (`ProjectPublicationController:41`, `Projects.tsx:45–53`). Les images projets pèsent environ 200 à 308 kB chacune.

**À faire :** découper les pages privées au chargement, ajouter pagination serveur avant croissance, formats/tailles d’images adaptés et mesures sur réseau mobile. Les champs de recherche ne constituent pas à eux seuls une recherche géographique.

### F26 — P2 — Découvrabilité et partage à terminer

`index.html` a une description générale ; les projets conservent le titre d’onglet « Projets — Belconnect ». Pas de sitemap/robots ou métadonnées sociales dédiées trouvés dans le dépôt.

**À faire après les blocages métier :** titre par fiche, aperçu de partage, URL canonique et indexation publique correcte. Les pages privées ne doivent pas être indexées. Le choix pré-rendu/SSR dépendra du besoin d’acquisition ; ne pas lancer une migration technique par réflexe.

### F27 — P1 — Documentation de progression trop historique

Le README contient encore des étapes où validation, gestion ou notifications sont « à développer », puis des sections ultérieures les déclarent réalisées. `SUIVI_CONFORMITE.md` est daté du 18 octobre ; `PERIMETRE_V1_WEB.md` est plus pertinent pour la sortie.

**Conséquence :** on confond « code écrit », « test local réussi » et « prêt à être utilisé publiquement ». C’est une cause directe des questions répétées sur le lot courant.

**À faire :** le plan lié en tête devient le tableau de sortie. Chaque lot a un état, une preuve et un responsable. Les anciens lots restent un historique, pas un certificat de fin.

### F28 — P2 pour le web — Mobile hors V1 et dépendances à traiter avant sa propre sortie

Les contrôles statiques mobile passent, mais npm signale 29 dépendances affectées, dont 18 de sévérité élevée. Plusieurs concernent Expo/Metro et la chaîne de développement : ce nombre ne signifie pas 29 failles exploitables dans l’application web.

**À faire :** maintenir mobile hors du lancement web ; audit de compatibilité Expo et correction ciblée avant reprise mobile. Ne pas utiliser un `audit fix --force` susceptible de casser les versions. Le mobile ne doit pas être présenté comme un produit Belconnect finalisé.

## Décisions de chef de projet

1. Arrêter les nouvelles fonctionnalités jusqu’à fermeture des lots de sortie.
2. Priorité à la cohérence des paiements et à l’indépendance des pages ; pas à une nouvelle refonte graphique.
3. Simplifier l’accès aux fonctions existantes, sans retirer discrètement les règles d’approbation déjà choisies.
4. Garder Stripe test tant que les états incohérents ne sont pas reproduits puis corrigés.
5. Préparer en parallèle l’identité légale, l’hébergement, l’e-mail et les contenus réels.
6. Ne jamais déclarer un lot terminé parce que son écran existe. La preuve doit inclure le parcours, le refus d’accès indu, l’erreur et la reprise.

**Verdict final :** une base fonctionnelle réutilisable, une façade publique présentable, mais une V1 commerciale encore non validée. Le travail restant consiste à fermer les risques et à rendre l’exploitation possible, pas à ajouter de nouveaux modules.
